# Data Model: Canonical Data Model & Vehicle Reference Catalog

## Raw Listing

Represents the original marketplace payload captured during ingestion.

**Fields**: marketplace source, ingestion run, source, uuid, raw payload, raw hash, adapter version, marketplace schema/payload versions, extracted timestamp, created timestamp.

**Rules**: Raw payload is immutable and remains unchanged during normalization, catalog synchronization, replay, and backfill. It is the audit source for marketplace-provided values.

## Listing

Represents the normalized operational listing consumed by backend reads and presentation experiences.

**Fields**: marketplace source, source, uuid, title, supported canonical categorical fields, numeric fields, free-text fields, status, first/last seen metadata, run references, current raw listing reference, canonical hash, normalization/canonicalization version, created/updated timestamps.

**Canonical categorical fields**: make, model, trim, fuel type, transmission, body type, seller type, vehicle condition, specs, and color.

**Rules**: Supported categorical values are stored as canonical keys. Numeric and free-text fields remain unchanged except for existing non-categorical normalization. Listing identifiers and history are preserved during backfill. Listing records retain the canonicalization or normalization rule version used during processing.

## Vehicle Reference Catalog

Represents the canonical vehicle reference database and is referred to as `vehicle_reference_catalog` when discussing the database object.

**Fields**: market, make key, make display, model key, model display, generation, body code, start year, end year, facelift start year, facelift end year, aliases, confidence, synchronization provenance, created/updated timestamps.

**Relationships**: Listing records reference catalog identity logically through canonical keys and market context. Aliases belong to catalog records. CSV reference files are the authoritative source for catalog content.

**Rules**: The catalog is the single source of truth for canonical vehicle identity, display names, vehicle generations, and market-specific vehicle metadata. Canonical keys are immutable once introduced. Display values may evolve without changing canonical keys. Catalog records are synchronized from CSV and include lightweight last-sync traceability.

## Reference File Set

Represents curated CSV files owned by data stewards.

**Fields**: market, make key, make display, model key, model display, generation, body code, year ranges, facelift ranges, aliases, confidence, source file metadata.

**Rules**: CSV files are authoritative. Synchronization is idempotent and repeatable. Invalid rows are reported and do not silently corrupt the database copy.

## Canonical Categorical Field

Represents a supported operational field normalized to deterministic canonical keys.

**Fields**: field name, raw value, canonical key, catalog match status, alias match status, unknown status.

**Rules**: Canonicalization removes formatting differences only and preserves semantic letters and numbers. Unknown values are canonicalized deterministically and reported for catalog improvement without blocking ingestion.

## Canonicalization Version

Represents the rule set used to canonicalize a listing.

**Fields**: version identifier, processing context, associated listing/run reference.

**Rules**: Every normalized listing records the version used during processing. Replay and backfill use explicit or recorded versions to remain deterministic. The model does not require a separate versioning service.

## Normalization Statistics

Represents operational reporting generated by ingestion, replay, synchronization, and backfill.

**Fields**: run or operation identifier, market, field name, known count, unknown count, unknown examples or counts, alias match count, catalog match count, rejected row count where applicable, timestamps.

**Rules**: Statistics support catalog improvement and operational monitoring. Unknown values never block ingestion by themselves. Reports must avoid logging sensitive raw payloads.

## State Transitions

**Catalog synchronization**: CSV row read → validated → inserted/updated/unchanged/rejected → synchronization report emitted → provenance updated for synchronized records.

**Listing ingestion**: raw payload captured → extracted → normalized → canonicalized with version → catalog lookup/alias resolution → persisted listing + immutable raw link → normalization statistics emitted.

**Backfill**: candidate listing selected → raw/source values resolved → canonicalized with selected version → dry-run/report or update → validation sample → rerun produces unchanged state when inputs are unchanged.
