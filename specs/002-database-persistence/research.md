# Phase 0 Research: Database Persistence Foundation

**Feature**: 002 — Database Persistence Foundation
**Date**: 2026-07-04
**Status**: Complete (all NEEDS CLARIFICATION resolved)

This document resolves the implementation decisions deferred by the
specification and the `Technical Context` of `plan.md`. The specification is
implementation-neutral regarding ORM/query-builder/library and migration
tooling; those choices are made here. **No business behavior or architecture
is changed** — only implementation technology is selected.

The Analysis Gate (Constitution "Analysis Gate") is satisfied: the affected
bounded context is **Data Ingestion**; data-quality implications are unchanged
from Feature 001 (validation/canonicalization/dedup gate runs before
persistence); historical-preservation implications are addressed by immutable
`RawListing`, append-only `ListingSnapshot`, and retained `IngestionRun` +
run reports (Constitution VII).

---

## R-1: PostgreSQL driver / database library

**Decision**: Use **`psycopg` 3** (the modern `psycopg` package,
`psycopg[binary,pool]`) as the PostgreSQL driver. Use it directly with
hand-written SQL inside `PostgresStorageAdapter`. **No ORM, no query
builder.**

**Rationale**:
- The spec mandates that the ingestion pipeline and `PersistenceService`
  remain independent of any specific ORM/query-builder/library (FR-060,
  NFR-003, SC-007). The cleanest way to guarantee that is to avoid ORMs
  entirely and confine the driver import to `src/db/connection.py` and
  `src/storage/postgres_storage.py`. `psycopg` 3 is a thin driver, not an
  ORM — it does not generate schema modules that could leak as imports.
- `psycopg` 3 has a native connection pool (`psycopg.pool`), prepared
  statements, and good JSONB support, and works against both local Postgres
  and Supabase (over TCP + TLS; compatible with pgBouncer in transaction
  pooling mode when using a connection pool per process).
- A thin driver keeps the `PostgresStorageAdapter` honest: it owns only DB
  calls and transactions, exactly as FR-002 requires. An ORM would tempt
  business-rule leakage into the adapter and would generate a schema module
  whose import would need to be guarded.
- Constitution XVI (Simplicity Over Complexity) + YAGNI: the persistence
  surface in this feature is small (upsert by source+uuid, snapshot insert,
  run resolution, raw read by run). SQL is the simplest tool that satisfies
  it without introducing an ORM's learning curve and coupling risk.

**Alternatives considered**:
- **SQLAlchemy (Core or ORM)** — more powerful, but adds a query-builder
  abstraction and (in ORM mode) schema-generated classes that increase the
  SC-007 grep surface and the coupling-leakage risk (R-002). Rejected for
  this feature; can be revisited by a future feature if query complexity
  grows.
- **Prisma (Python)** — the original suggestion; rejected by the spec's
  implementation-neutrality revision (no specific ORM mandated). Prisma's
  generated client would also create a schema module whose import boundary
  must be policed.
- **asyncpg** — excellent performance, but the Feature 001 pipeline is
  synchronous single-process; introducing async would complicate the runner
  for no benefit in this feature. Rejected.

## R-2: Migration tooling

**Decision**: Use **`yoyo-migrations`** with hand-written SQL migration files
stored under `src/db/migrations/`. Each migration has an `up` and a `down`
(Constitution "Migration Strategy": reversible, ordered, timestamped,
idempotent).

**Rationale**:
- `yoyo` is a lightweight, dependency-minimal migration tool that records
  applied migrations in a `yoyo_migration` bookkeeping table in the target
  database. It supports apply/rollback/status directly, matching the
  `migrate apply|status|rollback` CLI designed in Phase 1.
- It keeps migrations as plain SQL (no ORM DSL), so migrations are
  reviewable, reversible, and portable between local Postgres and Supabase.
- Constitution "Migration Strategy" requires ordered, timestamped,
  idempotent, reversible migrations with history preserved; `yoyo`'s
  timestamped filename ordering + down-migrations satisfy this directly.
- SC-005 (create full schema from empty DB) and US5 (idempotent, additive
  evolution) are naturally expressed as ordered SQL files.

**Alternatives considered**:
- **Alembic** — mature and widely used, but its primary mode is
  SQLAlchemy-autogenerated migrations, which would pull SQLAlchemy into the
  project and conflict with R-1's no-ORM decision. Alembic can be used
  standalone with raw SQL, but it is heavier than `yoyo` for this feature's
  scope. Rejected for simplicity (Constitution XVI).
- **Raw migration runner hand-rolled** — simplest, but reinvents
  bookkeeping, ordering, and reversibility that `yoyo` already provides
  reliably. Rejected (do not reinvent tooling).

## R-3: Connection management & pooling

**Decision**: A single `src/db/connection.py` module owns the `psycopg`
connection pool, created from `DATABASE_URL` with `DB_POOL_MIN`/`DB_POOL_MAX`
and `DB_CONNECT_TIMEOUT`. The `PostgresStorageAdapter` borrows a connection
per listing-unit transaction and returns it on commit/rollback. No global
session state outside the adapter.

**Rationale**:
- Keeps the driver import confined to two modules (R-1, SC-007).
- Per-listing atomic transactions (FR-054/055) map cleanly to
  `with conn.transaction(): ...` blocks in `psycopg` 3.
- Pooling reuses connections across listings within a run without exposing
  pool handles to the `PersistenceService` (the service asks the adapter for
  transaction control via the interface; it never sees a `Connection`).

**Alternatives considered**:
- A connection-per-run (no pool) — simpler, but a long run would hold one
  connection and re-open on failure; a pool is cheap and correct.
- An async pool — rejected with asyncpg (R-1).

## R-4: canonicalPayload & canonicalHash storage approach

**Decision**:
- Store `canonicalPayload` (and `raw_payload`, `config_snapshot`,
  `report_json`, `changed_fields`) as **`JSONB`** columns. `JSONB` gives
  binary storage, indexability, and native Postgres JSON ops; it is
  portable to Supabase.
- Generate `canonicalHash` / `snapshotHash` / `raw_hash` in **pure Python**
  (`src/common/canonical_hash.py`) before persistence — not in SQL — so the
  hash is deterministic and independent of the database. The hash is
  computed from the complete canonical listing state, order-independent
  where applicable (e.g., sort dict keys, sort list-valued fields of
  equivalent values), using a stable JSON canonicalization
  (`json.dumps(..., sort_keys=True, separators=(",", ":"))`) followed by
  `hashlib.sha256` and a hex digest (or a truncated hex for human-readable
  size where useful). The exact participating fields are an implementation
  detail documented here, not in the spec.

**Rationale**:
- Computing the hash in Python keeps the rule in the `PersistenceService`'s
  domain (it owns meaningful-change detection, FR-005) and out of the
  adapter (no business rule in the adapter — FR-061).
- `JSONB` preserves the "single `canonicalPayload`, no duplicated per-field
  columns" requirement (FR-022, SC-005) while remaining queryable for future
  analytics features (deferred).

**Participating canonical fields (implementation detail)**: the hash is
computed over the full canonical `Listing` domain object's meaningful fields
as represented in `to_record()`-equivalent canonical form (uuid, marketplace,
make, model, condition, price, currency, year, kilometers, fuel_type,
transmission, regional_spec, body_type, seller_type, location, photos_count,
source_url, normalization_version). Volatile metadata (`fetched_at`,
`first_seen_at`/`last_seen_at`, run ids, row timestamps) is **excluded** so
re-observation of an otherwise-unchanged listing does not create a snapshot.
This set may be refined during implementation; any refinement is documented
in `data-model.md`.

**Alternatives considered**:
- Computing the hash in SQL (e.g., `md5(jsonb::text)`) — would push a
  business rule (meaningful-change detection) into the adapter/SQL, violating
  FR-061. Rejected.
- Storing the payload as `JSON` (text) — loses binary efficiency and
  indexability. Rejected in favor of `JSONB`.
- Duplicated per-field snapshot columns — explicitly forbidden by FR-022 /
  SC-005. Rejected.

## R-5: Run-name slug rules & collision disambiguator

**Decision**: Generate the run name in pure Python (`src/common/run_naming.py`)
as `run_<marketplace>_<condition>_<make-or-scope>_<yyyyMMdd>_<HHmmss>` in UTC
(exactly FR-011a). Slug rules:
- Each segment is lowercased, ASCII-slugged: non-alphanumeric characters
  collapsed to a single `-`; leading/trailing `-` stripped; empty segments
  replaced by `unknown`.
- `<make-or-scope>` is the make slug when present, else a compact scope
  digest.
- Timestamp is UTC `yyyyMMdd_HHmmss` of the run start.
- **Disambiguator**: before insert, the service queries for an existing
  `ingestion_run.name` equal to the candidate. On collision, append a short
  `_<8-char hex>` suffix (random-free; derived from a deterministic input
  such as `sha1(candidate + run_id)[:8]` so it is reproducible from the
  inputs) and retry. The unique constraint on `ingestion_run.name`
  (Phase 2) is the backstop; on a rare unique-violation, the service retries
  with a fresh disambiguator. No `Math.random`/`Date.now` semantics matter
  here because this runs in the application, not in the workflow tool.

**Rationale**:
- The unique constraint (Phase 2) guarantees uniqueness at the DB level
  (R-009); the service-side probe + disambiguator keeps names human-readable
  while avoiding repeated constraint violations.
- Pure-Python generation keeps the rule in the `PersistenceService`'s domain
  (FR-005/FR-030), not in the adapter.
- Recorded in ADR-013 (FR-071).

**Alternatives considered**:
- A monotonic sequence suffix (`_001`, `_002`) — requires a per-scope counter
  table/state; more machinery than warranted (YAGNI). Rejected in favor of a
  deterministic short hex.
- Pure random suffix — non-reproducible from inputs. Rejected.

## R-6: Local development database vs Supabase

**Decision**: Support both. Default local dev path: **Docker Postgres**
(`docker run` one-liner in `quickstart.md`) with a local `DATABASE_URL`.
Production path: **Supabase** project URL. Both are exercised in integration
tests; tests use a `DATABASE_URL` pointing at the Docker service in CI and
skip when unavailable (with a clear marker).

**Rationale**:
- Keeps local development zero-cloud-cost and offline-capable while
  validating the production target (Supabase) in CI.
- `psycopg` 3 + `JSONB` + `yoyo` are portable between the two.

**Alternatives considered**:
- Supabase-only — blocks local/offline development and CI without secrets.
  Rejected.
- SQLite as a local substitute — would diverge from PostgreSQL's `JSONB`
  and constraint semantics, undermining SC-005/migration tests. Rejected.

## R-7: Transaction boundaries

**Decision**: One atomic transaction **per listing**, orchestrated by the
`PersistenceService`, executed by the `PostgresStorageAdapter` via the
interface's transaction-control operations (`begin_listing_unit` /
`commit` / `rollback`). The unit spans: `RawListing` persistence, `Listing`
insert/update, `ListingSnapshot` creation when required, current raw listing
reference update, `canonicalHash` update, and `firstSeen`/`lastSeen` lineage
update (FR-054). The `IngestionRun` row + run report are persisted once per
run (not per listing), outside the per-listing transactions.

**Rationale**:
- Per-listing atomicity (FR-054/055, NFR-010) gives partial-failure
  isolation: a single listing failure rolls back only that listing; the run
  continues and the run report records the failure (FR-056, SC-010).
- A single per-run transaction would roll back the entire run on one listing
  failure — too coarse and inconsistent with Feature 001 partial-failure
  behavior.

**Alternatives considered**:
- One transaction per run — rejected (too coarse; loses partial-failure
  isolation).
- One transaction per batch — adds batching complexity with no benefit for
  single-process run-on-demand scope (YAGNI). Rejected.

## R-8: StorageAdapter interface extension shape

**Decision**: Extend `src/storage/interface.py` **additively** (new methods
with default/no-op implementations or a capability protocol) so CSV and
in-memory adapters conform without behavior changes to Feature 001. New
operations: `upsert_listing`, `insert_snapshot`, `find_listing_by_source_uuid`,
`resolve_run`, `read_raw_for_run`, and transaction control
(`begin_listing_unit`/`commit`/`rollback`). Existing operations
(`write_raw`, `write_listings`, `write_report`, `read_raw`) remain unchanged
so the Feature 001 contract test stays green. The extension is recorded in
ADR-014 (FR-072, R-001a).

**Rationale**:
- Backward-compatible extension preserves Feature 001 (FR-062, NFR-008) and
  keeps substitutability (NFR-002).
- Default/no-op implementations on the existing adapters avoid modifying
  their Feature 001 behavior; the `PersistenceService` only invokes the new
  operations against the postgres backend (CSV/in-memory continue to be
  driven the Feature 001 way).

**Alternatives considered**:
- A separate `RelationalStorageAdapter` interface — would split the contract
  and weaken substitutability/SC-004. Rejected.
- Breaking changes to the four-operation interface — violates FR-062/NFR-008.
  Rejected.

## R-9: MarketplaceSource seeding

**Decision**: `MarketplaceSource` is reference/seeded data. The
`PersistenceService` upserts a `MarketplaceSource` row by `code` (e.g.,
`dubizzle`) at the start of a run when targeting a known marketplace, using
configuration-derived name/country/base URL (no marketplace-internal field
names). No admin UI (out of scope).

**Rationale**:
- Keeps `MarketplaceSource` independent of marketplace-internal field names
  (FR-010) and lets the `PersistenceService` operate on marketplace-agnostic
  domain objects.
- Avoids a manual seeding step while remaining idempotent (upsert by `code`).

**Alternatives considered**:
- A separate seeding CLI/migration with hardcoded rows — couples seed data
  to migrations and reduces flexibility. Rejected in favor of service upsert.
